# 1. Purpose

The WebSocket protocol powers the **real-time interview conversation** between the frontend and the Interview Engine.

REST APIs are responsible for creating and completing interview sessions.

WebSocket is responsible only for exchanging interview events while a session is active.

---

# 2. Connection Lifecycle

## WebSocket Endpoint

```text
GET /api/v1/ws/interviews/{sessionId}
```

### Authentication

The client connects using the authenticated session created through REST.

```
Authorization: Bearer <jwt-token>
```

### Connection Flow

1. Client creates an interview session using REST.
2. Client opens WebSocket using `sessionId`.
3. Backend validates JWT and session ownership.
4. Backend restores runtime state from Redis.
5. Backend sends the pending or first interviewer question.


### Implementation Notes

- Backend uses the Gorilla/WebSocket library for RFC 6455 compliant WebSocket connections.
- Frontend uses the browser's native WebSocket API.
- The WebSocket Manager maintains one active connection per interview session.
- The Interview Engine consumes WebSocket events and owns interview progression.

# 3. Message Envelope

Every WebSocket message uses the same structure.

```json
{
  "event": "QUESTION",
  "session_id": "session-uuid",
  "message_id": "message-uuid",
  "timestamp": "2026-08-28T12:35:12Z",
  "payload": {}
}
```

## Envelope Fields

| Field | Purpose |
|-------|---------|
| `event` | Message type. |
| `session_id` | Active interview session. |
| `message_id` | Unique message identifier. |
| `timestamp` | UTC timestamp generated by sender. |
| `payload` | Event-specific data. |

### Design Rules

- Every event has a unique `message_id`.
- Messages are processed independently.
- Unknown events are rejected with an error event.

# 4. Client → Server Events

The frontend sends interview events to the Interview Engine.

## Supported Events

| Event | Purpose |
|-------|---------|
| `ANSWER` | Submit candidate answer. |
| `REQUEST_HINT` | Request a hint. |
| `REQUEST_CLARIFICATION` | Ask interviewer to clarify. |
| `THINKING` | Candidate is thinking aloud. |
| `END_INTERVIEW` | Candidate ends interview. |
| `PING` | Heartbeat message. |

---

## ANSWER

### Payload

```json
{
  "answer": "Redis should persist interview session state..."
}
```

### Purpose

Submits a candidate answer for evaluation.

### Runtime Flow

1. Interview Engine receives answer.
2. Intent detection runs.
3. Technical evaluation runs.
4. Memory updates.
5. Next interviewer event is generated.

---

## REQUEST_HINT

### Payload

```json
{}
```

### Purpose

Candidate requests a directional hint.

Hint generation never changes interview state.

---

## REQUEST_CLARIFICATION

### Payload

```json
{}
```

### Purpose

Candidate asks interviewer to rephrase the current question.

The pending question remains unchanged.

---

## THINKING

### Payload

```json
{
  "message": "I'm thinking about Redis persistence first..."
}
```

### Purpose

Candidate communicates reasoning before giving the final answer.

Interview Engine responds with a thinking prompt if appropriate.

---

## END_INTERVIEW

### Payload

```json
{}
```

### Purpose

Candidate voluntarily ends the interview.

Interview completion workflow begins.

---

## PING

### Payload

```json
{}
```

### Purpose

Heartbeat used to keep the connection alive.

Updates Redis heartbeat timestamp.

---

# 5. Server → Client Events

The Interview Engine sends interview events to the frontend.

## Supported Events

| Event | Purpose |
|-------|---------|
| `QUESTION` | New interviewer question. |
| `HINT` | Hint response. |
| `CLARIFICATION` | Rephrased interviewer question. |
| `THINKING_RESPONSE` | Encourage reasoning. |
| `ANSWER_FEEDBACK` | Immediate feedback before next question. |
| `INTERVIEW_COMPLETED` | Interview completed successfully. |
| `PONG` | Heartbeat acknowledgement. |
| `ERROR` | Runtime error. |

---

## QUESTION

### Payload

```json
{
  "question_id": "question-uuid",
  "question": "What happens if Redis becomes unavailable while interview sessions are active?",
  "context_id": "ctx-project-1",
  "topic_id": "redis-topic-id"
}
```

### Purpose

Sends the next interviewer question.

### Design Rules

- One active pending question exists at a time.
- Question is stored in Redis before being sent.

---

## HINT

### Payload

```json
{
  "hint": "Think about how session recovery works when Redis becomes unavailable."
}
```

### Design Rules

- Hint never reveals the answer.
- Hint does not change runtime state.

---

## CLARIFICATION

### Payload

```json
{
  "clarification": "Assume Redis stores interview session state and becomes unavailable temporarily."
}
```

### Design Rules

- Clarification references the current pending question.
- No new question is generated.

---

## THINKING_RESPONSE

### Payload

```json
{
  "message": "You're thinking in the right direction. Explain how recovery would work step by step."
}
```

### Purpose

Encourages reasoning without providing the solution.

---

## ANSWER_FEEDBACK

### Payload

```json
{
  "summary": "Good explanation of Redis persistence. Let's go deeper into recovery."
}
```

### Purpose

Short interviewer transition before the next question.

---

## INTERVIEW_COMPLETED

### Payload

```json
{
  "session_id": "session-uuid",
  "status": "COMPLETED"
}
```

### Purpose

Signals the frontend that the interview has ended.

Frontend fetches evaluation through REST APIs.

---

## PONG

### Payload

```json
{}
```

Acknowledges heartbeat.

---

## ERROR

### Payload

```json
{
  "code": "INVALID_EVENT",
  "message": "Unsupported WebSocket event."
}
```

Used for runtime protocol errors.

# 6. Runtime Interview Flow

## Interview Conversation Flow

```text
Client
   │
   │ Connect
   ▼
Interview Engine
   │
QUESTION
   │
ANSWER
   │
Evaluate Answer
   │
Memory Update
   │
QUESTION / HINT / CLARIFICATION
   │
END_INTERVIEW
   ▼
INTERVIEW_COMPLETED
```

### Design Rules

- Only one interviewer question is pending.
- Every answer corresponds to the pending question.
- Runtime state is updated after evaluation.

---

# 7. Heartbeat Protocol

Heartbeats keep runtime interview sessions alive.

## Heartbeat Flow

```text
Client
   │
PING
   │
Interview Engine
   │
Update Redis heartbeat
   │
PONG
   ▼
Client
```

### Heartbeat Rules

| Rule | Value |
|------|-------|
| Ping interval | Every 30 seconds |
| Pong timeout | 10 seconds |
| Redis heartbeat update | Every successful ping |
| Missed heartbeat | Connection marked disconnected |

Heartbeat refreshes Redis TTL.

---

# 8. Reconnect Protocol

Reconnect restores runtime interview state without restarting the interview.

## Reconnect Flow

```text
Client reconnects
        │
Authenticate JWT
        │
Load Redis runtime state
        │
Restore pending question
        │
QUESTION event sent again
```

### Recovery Rules

- Pending question is restored from Redis.
- Gemini never regenerates the question.
- Candidate Memory is restored.
- Current context, topic, scenario, and difficulty remain unchanged.

# 9. Runtime Error Handling

## Error Event Format

```json
{
  "event": "ERROR",
  "session_id": "session-uuid",
  "message_id": "message-uuid",
  "timestamp": "2026-08-28T12:40:00Z",
  "payload": {
    "code": "SESSION_EXPIRED",
    "message": "Interview session has expired."
  }
}
```

## Runtime Error Codes

| Error Code | Description |
|------------|-------------|
| `INVALID_EVENT` | Unknown event received. |
| `INVALID_PAYLOAD` | Payload schema validation failed. |
| `SESSION_NOT_FOUND` | Session does not exist. |
| `SESSION_EXPIRED` | Redis runtime state expired. |
| `UNAUTHORIZED_SESSION` | User does not own session. |
| `INTERNAL_ERROR` | Unexpected runtime failure. |

# 10. Message Ordering Rules

| Rule | Description |
|------|-------------|
| One pending question at a time. | Prevent concurrent evaluations. |
| One answer per pending question. | Duplicate answers are ignored. |
| `message_id` identifies unique messages. | Prevent duplicate processing after reconnect. |
| Events are processed sequentially. | Preserve interview state consistency. |

### Duplicate Answer Rule

If the same `message_id` is received twice, the second event is ignored.

---

# 11. Connection State Rules

| Connection State | Description |
|------------------|-------------|
| CONNECTING | Client opening socket. |
| CONNECTED | Active interview connection. |
| RECONNECTING | Temporary disconnect recovery. |
| DISCONNECTED | Socket closed but Redis state still exists. |
| CLOSED | Interview completed or expired. |

### Transition Rules

- `CONNECTED → RECONNECTING` after missed heartbeat.
- `RECONNECTING → CONNECTED` after successful recovery.
- `CONNECTED → CLOSED` after interview completion.
- `DISCONNECTED → CLOSED` after Redis TTL expiry.

---

# 12. Design Rules

| Rule | Description |
|------|-------------|
| WebSocket handles runtime conversation only. | REST owns session creation and completion. |
| One active pending question exists at a time. | Prevent multiple evaluations simultaneously. |
| Redis owns runtime recovery state. | PostgreSQL owns permanent interview history. |
| Every event uses the standard message envelope. | Simplifies frontend and backend contracts. |
| Heartbeats refresh Redis TTL. | Runtime session stays alive during interview. |
| Reconnect restores runtime state without regenerating Gemini output. | Interview continuity is preserved. |
